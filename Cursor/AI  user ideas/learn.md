Как работают модели ИИ

Детерминированные и вероятностные
Традиционное ПО детерминировано. При одних и тех же входных данных повторный запуск программы даст тот же результат. Разработчик явно прописал код для работы по «проторенному пути».

С ИИ‑моделями не так. Они вероятностные. Это означает, что при одинаковом вводе модель может пойти по разным путям.

В разработке ПО использование разных модальностей может выглядеть так:

Описать текстом продукт или функцию, которую хотите создать, и вместе с ИИ определить план
Использовать изображения, чтобы поделиться макетами или дизайнами интерфейса, который вы создаете, или дать модели ИИ обратную связь, если не устраивают отступы или цвета
Пользоваться голосом, чтобы преобразовывать речь во входные данные для модели ИИ, избавляя от необходимости печатать длинные и подробные инструкции.

Галлюцинации

Представьте эти модели как очень мощное автодополнение текста. Если вы набрали «The weather today is...», телефон может подсказать «sunny» или «cloudy» по распространенным шаблонам. Модели ИИ делают то же самое, только с целыми концепциями и блоками кода.

Когда модель ИИ чего-то не знает, она не всегда говорит «I don't know». Вместо этого она генерирует то, что кажется наиболее вероятным, исходя из увиденных шаблонов. В контексте программирования это может означать:

Придумывание правдоподобно звучащих методов API, которых на самом деле не существует
Путаницу в синтаксисе между разными библиотеками или фреймворками
Создание параметров конфигурации, которые выглядят разумно, но на самом деле не реальны

// ИИ предлагает:
import { debounce } from "react";

// Реальность: debounce не экспортируется из React!
// Нужен lodash или собственная реализация

# ИИ предлагает:
df.remove_outliers(threshold=3)

# Реальность: у pandas DataFrames нет этого метода
# Вам нужно реализовать удаление выбросов самостоятельно

// ИИ предлагает для package.json:
{
  "type": "module",
  "exports": "./index.js",
  "browser": true // <- Это неверно!
}

Ваши запросы, как и ответы модели, становятся частью «контекста». Представьте контекст как длинный список — рабочую память для беседы, которую ведет модель ИИ.

В начале списка — системный промпт. Так создатель инструмента задает инструкции или стиль, которых должна придерживаться модель, включая конкретные правила, чтобы направлять ответы в нужную сторону.

Далее идет пользовательское сообщение или промпт — любые указания, которые вы хотите дать модели. Например, добавить новый маршрут для управления учетными записями пользователей. Можно не заморачиваться идеальной орфографией и грамматикой: модели ИИ обычно хорошо понимают смысл, хотя аккуратность не помешает.

# Что входит в вызов инструмента?

У каждого инструмента есть три основных компонента:

Имя, например read_file или search_web

Описание, которое указывает модели, когда и как использовать инструмент

Параметры — входные данные, необходимые инструменту для работы

Вот пример того, как может выглядеть определение инструмента:

``` json
{
  "name": "read_file",
  "description": "Читать содержимое файла из кодовой базы",
  "parameters": {
    "filepath": "Путь к файлу для чтения"
  }
}

```

Когда модель ИИ хочет использовать этот инструмент, она генерирует такой ответ:

``` json
{
  "tool": "read_file",
  "parameters": {
    "filepath": "src/components/Button.tsx"
  }
}

```

Определения инструментов включаются во входной контекст (обычно несколько сотен токенов на инструмент)
Результаты инструментов добавляются в выходной контекст (зависит от того, что возвращает инструмент)

Это значит, что беседы с активным использованием инструментов быстрее заполняют окно контекста и обходятся дороже. Но это обычно оправдано: с доступом к данным в реальном времени ИИ заметно полезнее.

# За пределами встроенных инструментов

Недавно появился новый стандарт — MCP (Model Context Protocol). Подумайте о нём как об универсальном способе для моделей ИИ использовать и интегрировать инструменты в разных приложениях.

Как USB стал стандартом подключения устройств к компьютерам, так и MCP стремится стать стандартом подключения инструментов к моделям ИИ. Это означает, что разработчики могут один раз создать инструмент, и он будет работать во множестве разных приложений с ИИ.

Например, вы можете использовать MCP для подключения к Figma (для работы с дизайн-файлами), к Linear (для просмотра и управления задачами) или даже к базе данных для прямых запросов к вашим данным. Вы также можете создавать собственные MCP‑серверы для интеграции с внутренними инструментами и API.

Теперь, когда вы понимаете принцип вызова инструментов, давайте посмотрим, что происходит, когда мы позволяем моделям ИИ использовать несколько инструментов последовательно. Вот тут и становится интересно — речь об агентах.

Хотя это не идеальное решение, это полезный ограничитель.*

# Понимание кодовой базы

Раньше работа с большой кодовой базой означала запоминание шаблонов регулярных выражений (regex) или изучение специализированных инструментов для эффективного поиска. 

*Агентский поиск*

``` json

Review the changes I've made to the discount code feature. Look for bugs, missing error handling, and anything that doesn't match our patterns in 
src/services/PricingService.ts
```

Хорошие подсказки для создания тестов:

"Спланируйте, как получить покрытие e2e для нашего процесса оформления заказа. Какие сценарии нам следует протестировать?"
"Настройте интеграционные тесты для платежного API. Используйте нашу существующую инфраструктуру тестирования в src/__tests__/".
"Какие крайние случаи не охвачены нашими текущими тестами для функции скидок?"
"Напишите регрессионные тесты для ошибки, которую мы исправили в PaymentService.ts".
